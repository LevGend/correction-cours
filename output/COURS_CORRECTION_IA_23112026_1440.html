      Comptes, droits et sudo

      sudo : principe

      sudo
      Théorie

      On ne travaille pas connecté en root (UID 0, tous les droits) : une faute de frappe pourrait tout casser. sudo <commande> exécute une seule commande avec les droits de root, la trace dans les journaux et retient le mot de passe 5 minutes. Sur Red Hat, il est réservé aux membres du groupe wheel.

      Pratique

      Avant de modifier un fichier de configuration : sudo cp fichier fichier.bak. Tester comme un autre compte sans son mot de passe : sudo -u cdurand <commande>.

      Exemple
      $ cat /etc/shadow
cat: /etc/shadow: Permission denied
$ sudo whoami
root
      Question de révision

      Pourquoi travaille-t-on avec sudo plutôt que connecté en root ?

      Réponse D. sudo exécute une seule commande avec les droits de root et la trace dans les journaux ; connecté en root, une faute de frappe peut tout casser.

      Comptes et groupes (T03)

      Fichiers des comptes
      Théorie

      Linux identifie un compte par son UID et un groupe par son GID. Trois fichiers : /etc/passwd (comptes, lisible par tous), /etc/shadow (mots de passe chiffrés et expiration, root seul), /etc/group (groupes et membres). On ne les modifie jamais à la main : useradd, groupadd, usermod, passwd, chage.

      Pratique

      Une ligne de /etc/passwd = 7 champs séparés par « : » : nom, x (mot de passe dans shadow), UID, GID du groupe principal, commentaire, dossier personnel, shell.

      Exemple
      $ getent passwd admin
admin:x:1000:1000:admin:/home/admin:/bin/bash
      Groupe principal et groupes secondaires
      Théorie

      Un compte a un seul groupe principal (il devient le groupe des fichiers qu'il crée) et autant de groupes secondaires qu'on veut (droits en plus).

      Pratique

      useradd -m -c "Prénom Nom" -g <principal> -G <secondaire> <login> : -m crée le dossier personnel, -g le groupe principal, -G les secondaires. usermod -aG wheel bob ajoute un groupe ; id vérifie.

      Exemple
      $ id cdurand
uid=...(cdurand) gid=...(compta) groupes=...(compta),...(nordlog)

      Sans -a, usermod -G wheel bob remplace tous les groupes secondaires de bob au lieu d'en ajouter un.

      Mot de passe provisoire
      Théorie

      chpasswd donne un mot de passe en lot (format login:motdepasse sur l'entrée) ; chage -d 0 force son changement à la 1re connexion.

      Pratique

      Vérification : sudo chage -l cdurand → « le mot de passe doit être changé ».

      Exemple
      echo "$LOGIN:$MDP" | chpasswd
chage -d 0 "$LOGIN"
      Question de révision

      Après usermod -G wheel bob, bob n'a plus accès au dossier de son service. Pourquoi ?

      Réponse C. Il fallait usermod -aG wheel bob ; sans -a, les anciens groupes secondaires sont remplacés.

      Script Bash idempotent (T03)

      Script Bash idempotent
      Théorie

      Un script fait toujours la même chose ; s'il vérifie avant d'agir, on peut le relancer sans danger : il est idempotent. Briques : shebang #!/bin/bash puis chmod +x, variable nom=valeur (sans espace autour du =, lue avec "$nom"), substitution $(commande), code retour $? (0 = succès), boucle, condition, fonction (paramètres $1, $2…).

      Pratique

      while IFS=';' read -r … lit un CSV ligne par ligne ; tail -n +2 saute l'en-tête ; if id "$LOGIN" &>/dev/null teste l'existence du compte (seul le code retour compte) ; ${1:-/root/employes.csv} = l'argument, sinon une valeur par défaut. Déboguer : bash -x script.sh.

      Exemple
      #!/bin/bash
FICHIER=${1:-/root/employes.csv}
creer_groupe() { getent group "$1" &>/dev/null || groupadd "$1"; }
tail -n +2 "$FICHIER" | while IFS=';' read -r PRENOM NOM SERVICE; do
    LOGIN=$(echo "${PRENOM:0:1}${NOM}" | tr '[:upper:]' '[:lower:]')
    creer_groupe "$SERVICE"
    if id "$LOGIN" &>/dev/null; then
        echo "$LOGIN existe déjà"
    else
        useradd -m -c "$PRENOM $NOM" -g "$SERVICE" -G nordlog "$LOGIN"
    fi
done

      2e lancement : uniquement des « existe déjà », aucune erreur.

      Dans un test [ ], les espaces après [ et avant ] sont obligatoires : [-f fichier] provoque une erreur. Tests utiles : -e existe, -f fichier, -d dossier, -s non vide, ! inverse.

      Question de révision

      On relance une 2e fois le script de création des comptes. Que doit-il se passer s'il est idempotent ?

      Réponse B. Le script vérifie avant d'agir (if id "$LOGIN") : relancé, il ne refait rien et n'échoue pas.

      Droits, SGID et ACL (T04)

      Droits rwx et notation octale
      Théorie

      Trois catégories (u propriétaire, g groupe, o autres) × trois droits : r = 4, w = 2, x = 1, additionnés par bloc (rwx = 7, r-x = 5, --- = 0). Sur un dossier, le sens change : r liste les noms, w crée/renomme/supprime dedans, x permet d'y entrer.

      Pratique

      chmod change les droits (750, u+x…), chown alice:compta le propriétaire et le groupe, chgrp le groupe. ls -ld dossier montre les droits du dossier lui-même. Un . après les droits signale une étiquette SELinux, un + une ACL.

      Exemple
      $ chmod 750 rapport.sh
$ ls -l rapport.sh
-rwxr-x--- 1 admin admin 120 Oct 26 10:00 rapport.sh

      Sur un dossier sans x, pas de cd, même avec r.

      Droits spéciaux : SGID et sticky bit
      Théorie

      Un 4e chiffre devant les droits. SGID (2, s à la place du x du groupe) : les fichiers créés dans le dossier prennent le groupe du dossier. Sticky bit (1, t ou T à la place du x des autres) : chacun ne supprime que ses propres fichiers (cas de /tmp, drwxrwxrwt).

      Pratique

      Dossiers de service : chmod 2770 → drwxrws---. Dossier commun : chmod 3770 (SGID + sticky) → drwxrws--T.

      Exemple
      sudo mkdir -p /srv/nordlog/{direction,compta,commercial,logistique,commun}
sudo chgrp compta /srv/nordlog/compta
sudo chmod 2770 /srv/nordlog/compta
sudo chgrp nordlog /srv/nordlog/commun
sudo chmod 3770 /srv/nordlog/commun
      ACL et ACL par défaut
      Théorie

      Les droits Unix ne connaissent qu'un seul groupe par fichier. Une ACL (Access Control List) donne des droits à un groupe ou un compte de plus. Une ACL par défaut (-d) sur un dossier est recopiée sur les fichiers créés ensuite dedans.

      Pratique

      setfacl -m ajoute ou modifie, getfacl lit. Pour un dossier, donner rx (lire et entrer).

      Exemple
      sudo setfacl -m g:direction:rx /srv/nordlog/compta
sudo setfacl -d -m g:direction:rx /srv/nordlog/compta
getfacl /srv/nordlog/compta    # group:direction:r-x et default:group:direction:r-x
      Question de révision

      Dans /srv/nordlog/compta en 2770, pourquoi un fichier créé par un membre appartient-il au groupe compta ?

      Réponse D. Le SGID sur un dossier fait hériter aux nouveaux fichiers le groupe du dossier.

      Règles sudo par service (T18)

      sudo et moindre privilège
      Théorie

      sudo lance une commande avec les droits d'un autre compte (root par défaut) si une règle l'autorise. Principe du moindre privilège : chacun reçoit les droits dont il a besoin, pas plus.

      Pratique

      Chacun utilise son propre mot de passe (pas celui de root) ; on donne un droit précis ; tout est tracé dans /var/log/secure. Sur AlmaLinux, le groupe wheel peut tout faire avec sudo (groupe sudo sur Ubuntu).

      Règle sudo
      Théorie

      Une ligne qui dit qui (% = un groupe), où (ALL = toutes les machines), en tant que qui ((root)) et quelles commandes (chemins complets, trouvés avec which). Avec des arguments, seuls ces arguments exacts sont permis.

      Pratique

      Les règles se rangent dans /etc/sudoers.d/, un fichier par besoin ; on ne touche pas à /etc/sudoers.

      Exemple

      /etc/sudoers.d/nordlog

      # NordLog : la logistique peut relancer l'intranet et lire ses journaux
%logistique ALL=(root) /usr/bin/systemctl restart httpd, /usr/bin/journalctl -u httpd

      En igarnier (groupe logistique) : sudo systemctl restart httpd fonctionne, sudo systemctl stop sshd est refusé.

      Une commande sans argument autorise tout : /usr/bin/systemctl seul permettrait aussi d'arrêter le pare-feu ou SSH. Un éditeur (vi), un visualiseur (less) ou find permettent d'ouvrir un shell root : autoriser sudo vi, c'est donner root.

      Question de révision

      Pourquoi ne pas autoriser %logistique ALL=(root) /usr/bin/systemctl sans argument ?

      Réponse A. Une commande sans argument autorise tout ; le moindre privilège impose les arguments exacts (restart httpd).

      visudo (T18)

      visudo
      Théorie

      Un fichier de règles mal écrit bloque tous les sudo, y compris le vôtre. visudo vérifie la syntaxe et refuse d'enregistrer un fichier faux (What now? : e pour corriger, x pour quitter sans enregistrer).

      Pratique

      Toujours visudo -f pour écrire, visudo -cf pour vérifier, sudo -l -U <compte> pour contrôler les droits d'un compte sans se connecter avec lui.

      Exemple
      sudo visudo -f /etc/sudoers.d/nordlog
sudo visudo -cf /etc/sudoers.d/nordlog   # parsed OK
sudo -l -U igarnier                      # exactement les 2 commandes

      Le nom d'un fichier de /etc/sudoers.d/ ne doit contenir ni point ni ~ : sinon il est ignoré, sans message. Pour qu'une règle %groupe s'applique, id <compte> doit montrer le groupe.

      Question de révision

      Pourquoi écrire les règles avec visudo -f plutôt qu'avec un éditeur quelconque ?

      Réponse C. Un fichier de règles mal écrit bloque tous les sudo, y compris le vôtre ; visudo refuse d'enregistrer un fichier faux.

      Stockage et disques

      Arborescence et espace disque (T02)

      Arborescence et points de montage
      Théorie

      Linux n'a qu'un seul arbre de dossiers, qui part de /. Chaque système de fichiers (XFS par défaut sur Red Hat, ou ext4) a sa propre taille et est accroché à un dossier : son point de montage. Sur srv-infra, / (8 Go) et /var (2 Go) sont séparés et ne partagent pas leur place libre : si /var (journaux, bases, fichiers en attente) déborde, le système continue de tourner.

      Pratique

      lsblk montre disques, partitions et volumes en arbre avec leur point de montage ; findmnt les montages en cours.

      Mesurer l'espace : df puis du
      Théorie

      Toujours dans cet ordre : df -h (disk free) dit quel système de fichiers est plein ; du -sh (disk usage) dit quel dossier ou fichier prend la place. -h affiche en Ko/Mo/Go.

      Pratique

      du -x reste sur le même système de fichiers, -s donne un total par dossier, 2>/dev/null cache les erreurs, | sort -h trie du plus petit au plus gros.

      Exemple
      df -h                                          # /var à environ 95 %
sudo du -xsh /var/* 2>/dev/null | sort -h      # /var/log en dernier
sudo du -sh /var/log/* | sort -h               # nordlog, environ 1,6 G
      Question de révision

      /var est plein à 95 %. Pourquoi le système continue-t-il de tourner ?

      Réponse B. / et /var sont séparés : si /var déborde, / garde sa place et le système continue de tourner.

      LVM et agrandissement (T02)

      LVM : PV, VG, LV
      Théorie

      LVM (Logical Volume Manager) empile trois couches entre le disque et les fichiers : le PV (disque ou partition donné à LVM) → le VG (réservoir d'espace) → le LV (volume taillé dans le VG, qui reçoit un système de fichiers). Un LV a deux noms équivalents : /dev/almalinux/var = /dev/mapper/almalinux-var.

      Pratique

      Afficher chaque couche : pvs, vgs, lvs. La colonne VFree de vgs est la réserve disponible pour agrandir.

      Exemple
      $ sudo vgs     # almalinux, VFree environ 1,91g
$ sudo lvs     # var : 2,00g
      Agrandir un volume à chaud
      Théorie

      Tant que le VG a de l'espace libre, on agrandit un LV serveur allumé, sans perte de données, en deux étapes : ① agrandir le volume, ② agrandir le système de fichiers (sinon df ne voit rien). L'option -r (resizefs) de lvextend enchaîne les deux.

      Pratique

      -L +1G ajoute 1 Go ; sans le +, la taille totale deviendrait 1 Go. Vérifier ensuite avec df -h /var (environ 3,0G, environ 65 %) et vgs (environ 0,9 Gio libre).

      Exemple
      sudo lvextend -r -L +1G /dev/almalinux/var
df -h /var

      XFS peut s'agrandir (xfs_growfs) mais pas rétrécir (ext4 peut les deux, avec resize2fs) : on ne pourra pas réduire /var plus tard. Et l'export ne se supprime pas : on agrandit.

      Question de révision

      Après lvextend -L +1G /dev/almalinux/var, df -h /var affiche toujours 2 G. Pourquoi ?

      Réponse D. Agrandir se fait en deux étapes (volume puis système de fichiers) ; -r enchaîne les deux, sinon df ne voit rien.

      Nouveau disque LVM (T13)

      La direction a fait installer un 2e disque (/dev/sdb, 8 Go) : il accueille les partages (lv_partages, 4 Go, XFS, /srv/partages) et les sauvegardes (lv_sauvegardes, 3 Go, ext4, /sauvegardes).

      Mettre en service un disque avec LVM
      Théorie

      On construit toutes les couches : le disque devient un volume physique (PV), placé dans un groupe de volumes (VG, le réservoir), où l'on taille des volumes logiques (LV) ; chaque LV est formaté (système de fichiers) puis monté sur un dossier.

      Pratique

      pvcreate → vgcreate <vg> <disque> → lvcreate -n <nom> -L <taille> <vg> → mkfs.xfs / mkfs.ext4 → mount. XFS (par défaut sur AlmaLinux) s'agrandit (xfs_growfs) mais ne se réduit pas ; ext4 peut être réduit, une fois démonté (resize2fs).

      Exemple
      lsblk /dev/sdb ; sudo wipefs /dev/sdb      # 8 Go, aucune signature : le disque est vide
sudo pvcreate /dev/sdb
sudo vgcreate vg_data /dev/sdb
sudo lvcreate -n lv_partages    -L 4G vg_data
sudo lvcreate -n lv_sauvegardes -L 3G vg_data
sudo mkfs.xfs  /dev/vg_data/lv_partages
sudo mkfs.ext4 /dev/vg_data/lv_sauvegardes
sudo mkdir -p /srv/partages /sauvegardes
sudo vgs vg_data                           # VFree 1020 Mo : il reste ~1 Go
      Question de révision

      Dans quel ordre met-on en service le 2e disque /dev/sdb ?

      Réponse A. Le disque devient PV, placé dans un VG, où l'on taille des LV qu'on formate puis monte.

      fstab et nofail (T13)

      /etc/fstab et l'option nofail
      Théorie

      Un mount à la main est perdu au redémarrage : /etc/fstab liste les montages faits au démarrage (6 champs : volume, dossier, type, options, sauvegarde, vérification). Une erreur dans fstab peut arrêter le serveur en mode urgence, sans SSH.

      Pratique

      nofail : si ce volume ne se monte pas, le serveur démarre quand même. Après chaque modification : systemctl daemon-reload (systemd relit fstab), findmnt --verify, puis mount -a, et seulement ensuite un redémarrage.

      Exemple
      /dev/vg_data/lv_partages     /srv/partages  xfs   defaults,nofail  0 0
/dev/vg_data/lv_sauvegardes  /sauvegardes   ext4  defaults,nofail  0 0
      sudo cp -a /etc/fstab /etc/fstab.avant-T13  # copie de secours avant d'éditer
sudo systemctl daemon-reload
sudo findmnt --verify       # « Succès, aucune erreur ni avertissement détecté »
sudo mount -a
df -h /srv/partages /sauvegardes   # 4,0G et 2,9G

      Pourquoi nofail est indispensable ici : ces volumes sont sur un 2e disque. S'il tombe en panne ou disparaît, sans nofail srv-infra s'arrête en mode urgence au démarrage, sans SSH : plus de DNS, DHCP, NTP pour tout le réseau privé à cause de simples données. Avec nofail, il démarre quand même.

      Question de révision

      Pourquoi l'option nofail est-elle indispensable pour les volumes du 2e disque ?

      Réponse B. Sans nofail, un volume absent bloque le démarrage en mode urgence : plus de DNS, DHCP, NTP pour le réseau privé.

      Quotas de groupe XFS
      Théorie

      Un quota limite l'espace d'un compte ou d'un groupe sur un système de fichiers : limite douce (bsoft) = avertissement, limite dure (bhard) = blocage avec « Disk quota exceeded ». Sous XFS, ils s'activent par une option de montage ; pour /, elle se donne au démarrage du noyau, d'où un redémarrage.

      Pratique

      sudo grubby --update-kernel=ALL --args="rootflags=gquota"
sudo systemctl reboot

sudo xfs_quota -x -c 'limit -g bsoft=80m bhard=100m commercial' /
sudo xfs_quota -x -c 'report -g -h' /

      Pourquoi l'activation des quotas de groupe sur / demande-t-elle un redémarrage ?

      Réponse C. Sous XFS, les quotas s'activent par une option de montage ; pour /, elle se donne au démarrage du noyau.

      Sécurité : SSH et SELinux

      Connexion SSH

      Connexion SSH
      Théorie

      SSH (Secure Shell) pilote une machine à distance par un canal chiffré, sur le port 22. Le client ssh (votre PC) envoie les commandes ; le serveur sshd (srv-infra) les exécute. À la 1re connexion, on accepte l'empreinte du serveur (yes), enregistrée dans ~/.ssh/known_hosts ; si elle change, SSH refuse la connexion (protection contre un faux serveur).

      Pratique

      L'invite [admin@srv-infra ~]$ indique le compte, la machine et le dossier (~ = dossier personnel). Le mot de passe ne s'affiche pas à la saisie.

      Exemple
      ssh admin@<IP de votre srv-infra>
ssh admin@<IP campus cli-01> hostname   # lance la commande à distance puis ferme la session
      Question de révision

      SSH refuse la connexion en signalant que l'empreinte du serveur a changé. Contre quoi ce comportement protège-t-il ?

      Réponse D. L'empreinte enregistrée dans ~/.ssh/known_hosts sert à reconnaître le serveur ; si elle change, SSH refuse.

      Clés SSH et sshd (T05)

      Authentification par clés SSH
      Théorie

      Une paire de clés remplace le mot de passe : la clé privée (id_ed25519) reste sur votre poste et ne se donne jamais ; la clé publique (id_ed25519.pub) est copiée sur chaque serveur dans ~/.ssh/authorized_keys. Une phrase de passe protège la clé privée si elle est volée.

      Pratique

      ssh-keygen -t ed25519 crée la paire (-N "" sans phrase de passe, -f le fichier) ; ssh-copy-id dépose la clé publique (sous Windows : type … | ssh …).

      Exemple
      ssh-keygen -t ed25519
ssh-copy-id admin@<IP srv-infra>     # Number of key(s) added: 1
ssh admin@<IP srv-infra>             # plus de mot de passe demandé

      SSH est exigeant sur les droits : ~/.ssh en 700, authorized_keys en 600.

      Configurer sshd
      Théorie

      On ne modifie pas /etc/ssh/sshd_config : on ajoute un fichier dans /etc/ssh/sshd_config.d/. Ces fichiers sont lus par ordre alphabétique et la première valeur lue gagne : un 10-… passe avant le 50-redhat.conf d'AlmaLinux.

      Pratique

      PermitRootLogin no (root interdit), MaxAuthTries 3 (3 essais), PasswordAuthentication no (clés seulement). sshd -t vérifie la syntaxe, sshd -T affiche la configuration réellement appliquée.

      Exemple
      sudo tee /etc/ssh/sshd_config.d/10-nordlog.conf > /dev/null << 'EOF'
PermitRootLogin no
MaxAuthTries 3
EOF
sudo sshd -t && sudo systemctl restart sshd
sudo sshd -T | grep -i permitrootlogin      # no

      Toujours sshd -t avant de redémarrer sshd (une erreur bloquerait toutes les nouvelles connexions), et garder une 2e session ouverte pendant les essais.

      Question de révision

      Après ssh-copy-id, SSH redemande toujours le mot de passe et ~/.ssh est en 777 sur le serveur. Quelle est la cause ?

      Réponse B. SSH refuse d'utiliser des clés dont les fichiers ont des droits trop ouverts : 700 pour le dossier, 600 pour authorized_keys.

      SELinux : contextes et modes (T06)

      SELinux et contextes
      Théorie

      SELinux (Security-Enhanced Linux) est un contrôle en plus des droits rwx, intégré au noyau : il décide quel programme peut toucher quel type de fichier, même lancé par root. Chaque fichier et processus porte une étiquette utilisateur:rôle:type:niveau ; c'est le type qui compte (sshd ne lit que ssh_home_t dans ~/.ssh).

      Pratique

      ls -Z (fichiers), ps -Z (processus) affichent l'étiquette ; chcon -t la change à la main ; restorecon remet l'étiquette prévue pour le chemin.

      Exemple
      $ ls -Z /etc/hostname
system_u:object_r:hostname_etc_t:s0 /etc/hostname
      Modes de SELinux
      Théorie

      enforcing applique les refus (normal), permissive laisse passer mais note les refus, disabled éteint (à éviter).

      Pratique

      getenforce ou sestatus : le mode actuel. setenforce 1 / 0 : change tout de suite, jusqu'au redémarrage. /etc/selinux/config : le mode au prochain démarrage.

      Exemple
      sudo setenforce 1
sudo sed -i 's/^SELINUX=permissive/SELINUX=enforcing/' /etc/selinux/config
getenforce        # Enforcing
      Diagnostiquer un refus SELinux
      Théorie

      Chaque refus est noté sous le nom AVC dans /var/log/audit/audit.log. On y lit qui est refusé (comm=), quoi (denied { read }), sur quel fichier (name=) et son étiquette (tcontext=).

      Pratique

      Symptôme du TD : la connexion par clé redemande le mot de passe, car authorized_keys a le type default_t au lieu de ssh_home_t. On corrige l'étiquette, sans désactiver SELinux.

      Exemple
      ls -Z ~/.ssh/authorized_keys          # ...default_t... au lieu de ssh_home_t
sudo ausearch -m avc -ts recent       # denied { read } ... comm="sshd"
restorecon -Rv ~/.ssh                 # Relabeled ... to ...ssh_home_t

      setenforce 0 n'est jamais la solution : on corrige l'étiquette (restorecon) ou le booléen (setsebool -P). Piège classique : un fichier déplacé avec mv garde son ancienne étiquette.

      Question de révision

      La connexion par clé redemande le mot de passe ; ls -Z montre default_t sur authorized_keys. Quelle est la bonne correction ?

      Réponse A. sshd ne lit que le type ssh_home_t ; restorecon remet l'étiquette prévue, sans désactiver SELinux.

      SELinux et partage Samba (T15)

      Contexte SELinux d'un dossier partagé
      Théorie

      SELinux n'autorise Samba à lire et écrire que les fichiers de type samba_share_t. chcon change l'étiquette temporairement (un restorecon la remet comme avant) ; semanage fcontext enregistre la règle dans la politique et restorecon l'applique : c'est la méthode permanente.

      Pratique

      semanage fcontext -a -t samba_share_t "<chemin>(/.*)?" puis restorecon -Rv <chemin> ; (/.*)? = le dossier et tout ce qu'il contient. semanage vient du paquet policycoreutils-python-utils.

      Exemple
      sudo semanage fcontext -a -t samba_share_t "/srv/partages/compta(/.*)?"
sudo restorecon -Rv /srv/partages/compta    # unlabeled_t -> samba_share_t
      Question de révision

      Pourquoi préférer semanage fcontext + restorecon à chcon pour étiqueter /srv/partages/compta ?

      Réponse D. semanage fcontext inscrit la règle, restorecon l'applique : c'est la méthode permanente.

      SELinux et site web (T17)

      Contexte SELinux d'un site web
      Théorie

      Le serveur web (httpd_t) ne lit que les fichiers de type httpd_sys_content_t. Un dossier hors de /var/www, ou un fichier déplacé (mv) depuis /home, garde une mauvaise étiquette : Apache répond 403 Forbidden malgré des droits Unix corrects.

      Pratique

      Diagnostiquer avec ls -Z et ausearch -m avc -ts recent ; réparer avec semanage fcontext + restorecon. Jamais setenforce 0, ni chmod 777.

      Exemple

      Standard du T17 : servir le site depuis /srv/intranet.

      sudo semanage fcontext -a -t httpd_sys_content_t "/srv/intranet(/.*)?"
sudo restorecon -Rv /srv/intranet

      Dans intranet.conf : DocumentRoot /srv/intranet, <Directory /srv/intranet/direction>, et un bloc <Directory /srv/intranet> avec Require all granted, puis sudo httpd -t et sudo systemctl restart httpd.

      Question de révision

      Une page index.html déplacée avec mv depuis /home donne 403 Forbidden, alors que ses droits Unix sont corrects. Pourquoi ?

      Réponse C. Un fichier déplacé garde son étiquette ; httpd ne lit que httpd_sys_content_t, d'où le 403.

      Utilisateur SELinux user_u
      Théorie

      SELinux peut associer un compte Linux à un utilisateur SELinux restreint : user_u ne peut plus utiliser su ni sudo, même avec le bon mot de passe. C'est SELinux qui bloque, pas les droits Unix.

id -Z        # user_u:user_r:user_t ; su - est refusé

      fbenali tape le bon mot de passe mais su - est refusé. Qu'est-ce qui le bloque ?

      Réponse A. user_u ne peut plus utiliser su ni sudo, même avec le bon mot de passe : c'est SELinux qui bloque.

      Théorie

      Théorie

      Zones firewalld (T07, T09)

      Zones firewalld
      Théorie

      firewalld range les interfaces dans des zones (niveaux de confiance), chacune avec ses services autorisés : ici ens33 dans public (le campus) et vxlan0 dans internal (le réseau NordLog).

      Pratique

      --permanent enregistre la règle, --reload l'applique ; --list-all --zone=internal affiche une zone.

      Exemple
      sudo firewall-cmd --permanent --zone=public --add-port=8080/tcp
sudo firewall-cmd --reload
sudo firewall-cmd --zone=public --list-ports

      Une règle --permanent ne s'applique qu'après --reload ; sans --permanent, elle s'applique tout de suite mais disparaît au redémarrage.

      Zones firewalld
      Théorie

      Une zone = un niveau de confiance, avec la liste des services autorisés pour ce qui arrive par elle. (La zone s'applique à l'interface, pas au subnet : le pare-feu regarde *par où* arrive le paquet.) Une zone se lie à une interface (par où arrive le paquet) ou à une source (un réseau, --add-source=…) ; ici, on la lie à l'interface.

      Pratique

      public pour le campus (le minimum), internal pour le réseau privé, où l'on ouvre DHCP, DNS et NTP. Sur AlmaLinux, la zone d'une interface se règle dans la connexion NetworkManager (connection.zone).

      Exemple
      sudo firewall-cmd --permanent --zone=internal --add-service={dhcp,dns,ntp}
sudo firewall-cmd --permanent --zone=public --remove-service=dhcp   # le campus n'en a pas besoin
sudo firewall-cmd --reload
sudo firewall-cmd --zone=internal --list-services

      Routage et NAT (T08)

      Route par défaut
      Théorie

      Pour joindre une adresse hors de ses réseaux, une machine envoie le paquet à sa passerelle : c'est la route par défaut (default via <passerelle> dans ip route). Une machine n'a qu'une route par défaut utile.

      Pratique

      cli-01 doit sortir par srv-infra (192.168.100.1) : ipv4.gateway sur lab, et ipv4.never-default yes sur ens33 (qui ne donne plus de route par défaut). Poser le filet at avant.

      Exemple
      sudo nmcli connection modify lab ipv4.gateway 192.168.100.1
sudo nmcli device reapply vxlan0

sudo nmcli device reapply ens33

tracepath -n almalinux.org       # passe d'abord par 192.168.100.1
      NAT (masquerade) et politique firewalld
      Théorie

      Internet ne sait pas répondre à une adresse privée. Le NAT (Network Address Translation) : srv-infra remplace l'adresse source par la sienne à l'aller et fait l'inverse au retour. Dans firewalld, il s'appelle masquerade.

      Pratique

      --add-masquerade sur la zone de sortie (public) + une politique qui autorise le passage de la zone internal (ingress) vers la zone public (egress). sysctl net.ipv4.ip_forward doit valoir 1 (srv-infra route les paquets).

      Exemple
      sudo firewall-cmd --permanent --zone=public --add-masquerade
sudo firewall-cmd --permanent --new-policy lan-internet
sudo firewall-cmd --permanent --policy lan-internet --add-ingress-zone internal
sudo firewall-cmd --permanent --policy lan-internet --add-egress-zone public
sudo firewall-cmd --permanent --policy lan-internet --set-target ACCEPT
sudo firewall-cmd --reload
      Question de révision

      Pourquoi srv-infra doit-il faire du NAT (masquerade) pour que cli-01 accède à Internet ?

      Réponse B. Le NAT remplace l'adresse source privée par celle de srv-infra à l'aller et fait l'inverse au retour.

      Théorie

      DNS avec bind (T09)

      DNS : traduire les noms en adresses
      Théorie

      Traduire un nom (intranet.nordlog.lan) en adresse IP. srv-infra fait autorité sur nordlog.lan et relaie vers 8.8.8.8 (forwarder) les noms qu'il ne connaît pas.

      Pratique

      named (bind) : paquets bind et bind-utils à installer sur srv-infra (bind-utils fournit dig). dig interroge un serveur DNS précis.

      Exemple
      dig @192.168.100.1 intranet.nordlog.lan +short
      dig @192.168.100.1 almalinux.org +short     # nom externe : la réponse passe par le relais 8.8.8.8

      @ = le serveur interrogé ; +short = seulement la réponse.

      #### /etc/named.conf – ce que j'ai modifié

      listen-on port 53 { 127.0.0.1; 192.168.100.1; };   // écouter aussi sur le réseau privé
allow-query     { localhost; 192.168.100.0/24; };    // répondre au réseau privé
forwarders      { 8.8.8.8; };                        // relais pour les noms inconnus

zone "nordlog.lan" IN {
    type master;
    file "nordlog.lan.zone";     // relatif à /var/named/
};

      Les trois premières lignes se placent dans le bloc options { … } ; le bloc zone se place à la fin du fichier.

      Par défaut, bind n'écoute que sur 127.0.0.1 et ne répond qu'à localhost : il faut l'ouvrir explicitement au réseau privé. allow-query liste tous les clients autorisés : un nouveau client sur un autre réseau (par exemple un conteneur, voir T16) sera refusé tant qu'on ne l'y inscrit pas.

      #### Le fichier de zone : comment il se lit

      Fichier de zone
      Théorie

      Le fichier qui décrit les noms d'un domaine (ici /var/named/nordlog.lan.zone). Chaque ligne = un enregistrement : <nom> IN <type> <valeur>.

      Pratique

      Déclaré dans named.conf (type master; file "nordlog.lan.zone";), lu par named ; vérifié avec named-checkzone. Types principaux : SOA, NS, A, CNAME.

      Exemple
      $TTL 3600
@   IN SOA srv-infra.nordlog.lan. admin.nordlog.lan. (
        2026112301 ; serial (AAAAMMJJnn) – à augmenter à chaque modif
        3600       ; refresh
        900        ; retry
        604800     ; expire
        300 )      ; TTL négatif
    IN NS    srv-infra.nordlog.lan.

srv-infra   IN A     192.168.100.1
cli-01      IN A     192.168.100.10
intranet    IN CNAME srv-infra

      $TTL 3600 : durée pendant laquelle les réponses peuvent être gardées en mémoire.

      TypeSensExemple
      SOAStart Of Authority : carte d'identité de la zone (obligatoire, en premier)@ IN SOA srv-infra.nordlog.lan. admin.nordlog.lan. ( … )
      NSName Server : quel serveur DNS répond pour la zoneIN NS srv-infra.nordlog.lan.
      Anom → Adresse IPv4cli-01 IN A 192.168.100.10
      CNAMEalias → vers un autre nomintranet IN CNAME srv-infra

      Règles des noms :

      • @ = le domaine lui-même (nordlog.lan.).
      • Nom court (cli-01) → bind ajoute le domaine → cli-01.nordlog.lan.
      • Nom qui finit par un point (srv-infra.nordlog.lan.) = nom complet, bind n'ajoute rien.
      • ⚠️ Nom complet sans point final → bind ajoute le domaine une 2e fois (srv-infra.nordlog.lan.nordlog.lan).
      • Une ligne qui commence par des espaces reprend le nom de la ligne au-dessus.

      #### Les 5 nombres du SOA : ( 2026112301 3600 900 604800 300 )

      Ils servent quand il y a plusieurs serveurs DNS pour la même zone : un primaire (master, ici srv-infra) qui a le vrai fichier, et des secondaires (slaves) qui en gardent une copie. Les nombres disent aux secondaires comment rester à jour. Toutes les durées sont en secondes.

      PositionValeurNomCe que ça veut dire
      12026112301Serial (numéro de série)« Version » de la zone, au format AAAAMMJJnn (date + compteur du jour). Le secondaire compare ce numéro avec le sien : s'il est plus grand, il recopie la zone. ⇒ À augmenter à chaque modification, sinon les secondaires ne voient pas le changement. Maximum 10 chiffres.
      23600 (1 h)RefreshToutes les heures, le secondaire demande au primaire « ton serial a changé ? ».
      3900 (15 min)RetrySi le primaire ne répond pas, le secondaire réessaie toutes les 15 min.
      4604800 (7 jours)ExpireSi le primaire reste injoignable 7 jours, le secondaire arrête de répondre pour la zone (ses données sont trop vieilles pour être fiables).
      5300 (5 min)TTL négatifQuand un nom n'existe pas, les autres serveurs gardent cette réponse « n'existe pas » 5 min en cache avant de redemander.

      Moyen mnémotechnique : Série, Rafraîchir, Réessayer, Expirer, Négatif → « SRREN ».

      Dans notre TP il n'y a qu'un seul serveur DNS : seuls le serial et le TTL négatif ont un effet réel seul le TTL négatif a un effet réel ; le serial ne sert qu'aux secondaires, mais on l'augmente quand même à chaque modification (règle du cours, indispensable dès qu'un secondaire existe). On met quand même les 5 valeurs car le format du SOA les exige.

      NFS (T14)

      La logistique veut retrouver la documentation des procédures sur ses postes, sans rien avoir à faire : srv-infra exporte /srv/partages/doc en NFS, cli-01 le monte à la demande avec autofs.

      NFS : partager un dossier entre machines Linux
      Théorie

      Le serveur exporte un dossier pour un réseau, avec des options ; le client le monte dans un de ses dossiers. La version 4 du protocole (nfs4) est utilisée par défaut.

      Pratique

      Serveur : /etc/exports.d/*.exports, service nfs-server, exportfs -rav (relit et affiche les exports). Client : showmount -e <serveur>, mount -t nfs. Options : rw / ro, sync (écrit sur disque avant de répondre), root_squash (root sur le client n'est pas root sur le partage). Pas d'espace avant la parenthèse.

      Exemple
      # srv-infra
sudo dnf install -y nfs-utils
echo "/srv/partages/doc 192.168.100.0/24(rw,sync,root_squash)" | sudo tee /etc/exports.d/doc.exports
sudo systemctl enable --now nfs-server
sudo exportfs -rav           # exporting 192.168.100.0/24:/srv/partages/doc
sudo firewall-cmd --permanent --zone=internal --add-service={nfs,mountd,rpc-bind}
sudo firewall-cmd --reload
# cli-01
showmount -e 192.168.100.1   # /srv/partages/doc 192.168.100.0/24
      • Pare-feu : nfs suffit en NFSv4 ; mountd et rpc-bind servent à showmount.
      • Pour un montage NFS dans /etc/fstab, l'option _netdev fait attendre le réseau avant de monter.
      • Avec un espace avant la parenthèse (192.168.100.0/24 (rw…)), les options s'appliqueraient à tout le monde, et plus seulement au réseau privé.
      • root_squash : root sur cli-01 devient nobody sur le partage ; un client compromis ne peut pas agir en root sur les fichiers du serveur.
      Question de révision

      Ligne d'export : /srv/partages/doc 192.168.100.0/24 (rw,sync,root_squash). Quel est le problème ?

      Réponse B. Pas d'espace avant la parenthèse, sinon les options ne sont plus liées au réseau indiqué.

      Apache httpd (T17)

      Serveur web Apache (httpd)
      Théorie

      Un serveur web attend les demandes des navigateurs et leur renvoie des pages, en HTTP (port 80 ; HTTPS chiffré : port 443). Une requête vers l'intranet passe par 3 étapes : DNS (le nom donne 192.168.100.1), pare-feu (service http ouvert dans la zone internal), puis Apache (hôte virtuel, puis fichier du DocumentRoot). Si une étape échoue, les suivantes n'ont pas lieu.

      Pratique

      Paquet et service httpd sur AlmaLinux (apache2 sur Ubuntu). Configuration principale /etc/httpd/conf/httpd.conf (on n'y touche pas) ; un fichier par site dans /etc/httpd/conf.d/*.conf ; erreurs dans /var/log/httpd/error_log.

      Exemple
      sudo dnf install -y httpd
echo "Intranet NordLog" | sudo tee /var/www/html/index.html
sudo httpd -t                          # doit répondre Syntax OK
sudo systemctl enable --now httpd
sudo firewall-cmd --permanent --zone=internal --add-service=http
sudo firewall-cmd --reload

      sudo echo "…" > fichier ne marche pas : la redirection > est faite par votre shell, qui n'a pas les droits root. On écrit avec | sudo tee fichier. Un fichier de conf.d/ qui ne finit pas par .conf n'est pas lu.

      Question de révision

      sudo echo "Intranet" > /var/www/html/index.html répond Permission denied. Pourquoi ?

      Réponse A. sudo ne s'applique qu'à echo ; la redirection reste faite par le shell de l'utilisateur.

      Hôte virtuel protégé (T17)

      Hôte virtuel
      Théorie

      Un site déclaré dans Apache : un seul serveur peut héberger plusieurs sites, reconnus par le nom tapé dans la barre d'adresse. Le bloc commence par <VirtualHost *:80> et se ferme par </VirtualHost>.

      Pratique

      ServerName choisit le site, DocumentRoot donne le dossier des pages (/ = DocumentRoot/index.html), <Directory chemin> fixe des règles pour un dossier et ses sous-dossiers.

      Exemple

      /etc/httpd/conf.d/intranet.conf

      <VirtualHost *:80>
    ServerName intranet.nordlog.lan
    DocumentRoot /var/www/html
    <Directory /var/www/html/direction>
        AuthType Basic
        AuthName "Espace direction"
        AuthUserFile /etc/httpd/.htpasswd
        Require valid-user
    </Directory>
</VirtualHost>
      Authentification Basic et .htpasswd
      Théorie

      Une fenêtre demande un compte et un mot de passe avant d'afficher un dossier. Les comptes sont des comptes web stockés dans un fichier .htpasswd (mot de passe chiffré), distincts des comptes Linux.

      Pratique

      Quatre directives dans le <Directory> à protéger : AuthType Basic, AuthName "…" (message affiché), AuthUserFile (le fichier des comptes), Require valid-user (tout compte du fichier peut entrer). Le fichier se crée avec htpasswd.

      Exemple
      sudo htpasswd -c /etc/httpd/.htpasswd amartin      # -c : 1er compte seulement
# depuis cli-01
curl http://intranet.nordlog.lan/                   # page d'accueil
curl -I http://intranet.nordlog.lan/direction/      # HTTP/1.1 401 Unauthorized
curl -u amartin:<mot de passe> http://intranet.nordlog.lan/direction/   # Espace direction

      Relancé avec -c, htpasswd écrase le fichier et les comptes déjà créés. Avec Basic, le mot de passe circule simplement encodé, pas chiffré : en entreprise, seulement en HTTPS. Le 401 sans compte n'est pas une panne : c'est la preuve que la protection fonctionne.

      Question de révision

      Pourquoi un 401 sur /direction/ sans compte n'est-il pas une panne ?

      Réponse B. Sans compte, le 401 montre que l'accès est bien protégé.

      sudo systemctl enable --now cockpit.socket, puis connexion avec le compte admin par le tunnel.

      Question de révision

      Pourquoi faut-il ssh -L pour ouvrir Cockpit depuis le PC de la salle ?

      Réponse D. Le tunnel transporte le port 9090 dans la connexion SSH, seul port ouvert.

      Conteneurs Podman et quadlet (T16)

      Image, conteneur, volume (Podman)
      Théorie

      Une image est un modèle prêt à l'emploi (une application et tout ce dont elle a besoin) ; un conteneur est une image en cours d'exécution, isolée du système ; un volume est un espace de stockage qui survit au conteneur.

      Pratique

      Podman (compatible Docker) : podman pull (télécharger une image), podman run -p 127.0.0.1:8080:80 (publier un port en local seulement), podman ps, podman logs <nom>. Vérifier d'abord la place dans /var : l'image fait environ 500 Mo.

      Exemple
      df -h /var                                   # 1,2 Go libres avant ; 536 Mo après l'image (83 %)
sudo podman pull docker.io/louislam/uptime-kuma:1

      Les données d'Uptime Kuma survivent à la suppression du conteneur parce qu'elles sont dans le volume uptime-kuma-data (sous /var/lib/containers/storage/volumes/), pas dans le conteneur.

      Quadlet : un conteneur géré comme un service
      Théorie

      Un conteneur lancé à la main ne redémarre pas tout seul après un redémarrage du serveur. Avec quadlet, on le décrit dans un fichier .container placé dans /etc/containers/systemd/, et systemd en fait un service comme les autres.

      Pratique

      systemctl daemon-reload crée le service, qui porte le nom du fichier (uptime-kuma.container → uptime-kuma.service) ; systemctl start le démarre. La section [Install] suffit au démarrage automatique.

      Exemple

      /etc/containers/systemd/uptime-kuma.container :

      [Unit]
Description=Uptime Kuma (supervision NordLog)

[Container]
Image=docker.io/louislam/uptime-kuma:1
ContainerName=uptime-kuma
PublishPort=127.0.0.1:3001:3001
Volume=uptime-kuma-data:/app/data

[Service]
Restart=always

[Install]
WantedBy=multi-user.target
      sudo systemctl daemon-reload
sudo systemctl start uptime-kuma     # uptime-kuma.container -> uptime-kuma.service
systemctl status uptime-kuma         # active (running)
sudo ss -tlnp | grep 3001            # 127.0.0.1:3001 seulement

      PublishPort=127.0.0.1:3001:3001 : joignable uniquement depuis le serveur (et donc par le tunnel), le port n'est pas ouvert dans le pare-feu. Un service généré par quadlet ne s'active pas avec systemctl enable : c'est [Install] qui s'en charge.

      Question de révision

      Uptime Kuma, lancé avec podman run, n'est pas revenu après un redémarrage du serveur. Quelle est la solution du cours ?

      Réponse B. Avec quadlet, systemd fait du conteneur un service comme les autres.

      Supervision Uptime Kuma (T16)

      Supervision et sondes
      Théorie

      Superviser = surveiller les services ; une sonde teste un service à intervalles réguliers et alerte quand il tombe.

      Pratique

      Uptime Kuma, avec 3 sondes : ping de cli-01, port TCP 22 de srv-infra, DNS intranet.nordlog.lan (serveur 192.168.100.1).

      Exemple

      Sondes créées : cli-01 (ping) → 192.168.100.10 ; srv-infra (SSH 22) → TCP 192.168.100.1:22 ; DNS intranet.nordlog.lan → serveur 192.168.100.1. Test d'alerte : sur cli-01, sudo systemctl stop sshd, attendre 1 minute, puis sudo systemctl start sshd.

      La sonde DNS était rouge : queryA EREFUSED intranet.nordlog.lan. Le journal de bind donne la cause :

      named[…]: client 10.88.0.2#35398 (intranet.nordlog.lan): query 'intranet.nordlog.lan/A/IN' denied

      Le conteneur n'interroge pas depuis 192.168.100.x mais depuis le réseau interne de Podman (10.88.0.0/16, ici 10.88.0.2). Or allow-query (T09) n'autorise que localhost et 192.168.100.0/24 : bind refuse. Correction dans /etc/named.conf (copie de secours named.conf.avant-T16) :

      allow-query     { localhost; 192.168.100.0/24; 10.88.0.0/16; };
      sudo named-checkconf && sudo systemctl reload named

      Une minute plus tard, la sonde est verte. Leçon : un conteneur a sa propre adresse, il faut le compter comme un client de plus.

      Question de révision

      La sonde DNS est rouge (EREFUSED) ; le journal de bind montre client 10.88.0.2 ... denied. Quelle est la correction ?

      Réponse A. Le conteneur interroge depuis le réseau interne de Podman, absent d'allow-query : bind refuse.

      Exploitation du serveur

      Processus et priorités (T12)

      La compta : le serveur est très lent depuis le lancement de l'export de la logistique. Il faut mesurer, identifier les processus responsables, baisser leur priorité, puis les arrêter.

      Processus et charge du serveur
      Théorie

      Un processus est un programme en cours d'exécution, identifié par un numéro unique, le PID, avec sa part de processeur (%CPU) et de mémoire (%MEM). La charge moyenne est le nombre moyen de tâches qui attendent le processeur (1, 5 et 15 min) : proche du nombre de processeurs, le serveur est saturé.

      Pratique

      uptime (charge), free -h (mémoire : lire la colonne available), top (en direct : P tri par CPU, M par mémoire, c commande complète, q quitter), ps aux --sort=-%cpu (photo, les plus gourmands en premier).

      Exemple
      uptime                       # load average: 1,40, 0,43, 0,15 (monte vers 2) ; srv-infra a 2 processeurs
free -h                      # 1,4 Gi disponibles : la mémoire n'est pas en cause, c'est le CPU
ps aux --sort=-%cpu | head -4
      PID%CPUNI d'origineCommande complète
      4504699,8-5nordlog-export /dev/zero
      4504799,4-5nordlog-export /dev/zero

      Deux processus root, un processeur chacun : le serveur est saturé.

      • Le nom affiché nordlog-export cache le vrai programme, sha256sum : ps -o pid,ni,args -C sha256sum le retrouve par son nom de programme (-C). Le nom a été changé au lancement avec exec -a ; sha256sum /dev/zero lit des zéros à l'infini et ne s'arrête jamais seul.
      Priorité : la valeur nice
      Théorie

      De -20 (le plus prioritaire, réservé à root) à 19 (le plus « gentil », laisse passer tous les autres) ; 0 par défaut. Changer la priorité ralentit un processus sans l'arrêter.

      Pratique

      renice -n 19 -p <PID> sur un processus qui tourne déjà ; ps -o pid,ni,args affiche la valeur nice (colonne NI).

      Exemple
      sudo renice -n 19 -p 45046 45047         # priorité précédente -5, nouvelle priorité 19
ps -o pid,ni,pcpu,args -p 45046,45047    # NI = 19, mais toujours ~100 % CPU

      Toujours ~100 % : personne d'autre ne demande le processeur, il n'y a donc personne à laisser passer. Le nice ne fait effet que s'il y a concurrence.

      Signaux : arrêter un processus
      Théorie

      Un signal est un message envoyé à un processus. SIGTERM (15) demande l'arrêt : le programme peut finir proprement ; SIGKILL (9) l'arrête immédiatement, sans nettoyage.

      Pratique

      kill <PID> (15), kill -9 <PID> seulement en dernier recours, pkill <nom> pour désigner les processus par leur nom (-f : cherche dans la commande complète).

      Exemple
      sudo kill 45046 45047        # SIGTERM : arrêt propre
uptime                       # 0,56 une minute plus tard, contre 1,41 ; top : 94 % de CPU libre

      pgrep -f / pkill -f nordlog-export cherchent le mot dans toute la ligne de commande, y compris celle de sa propre session si elle contient ce mot : le kill a coupé la session SSH. Plus sûr : pgrep -x sha256sum (nom exact du programme), ou relire la liste des PID avant de tuer.

      Question de révision

      Serveur lent : uptime donne une charge proche de 2 sur 2 processeurs, free -h montre 1,4 Gi disponibles. Conclusion ?

      Réponse D. Une charge proche du nombre de processeurs signale la saturation ; la mémoire disponible reste large.

      Paquets et mises à jour (T19)

      Paquets, dépôts, dnf et rpm
      Théorie

      Un paquet (RPM) contient un logiciel, sa version et ses dépendances, que dnf installe automatiquement. Un dépôt met des paquets à disposition ; il est déclaré dans /etc/yum.repos.d/. dnf installe et met à jour ; rpm interroge ce qui est installé.

      Pratique

      Dépôts AlmaLinux 9 : baseos (noyau, outils, bibliothèques), appstream (httpd, bind, samba…), extras. Équivalent Ubuntu : apt.

      Exemple
      dnf repolist              # appstream, baseos, extras
rpm -q tree               # installé ? quelle version ?
rpm -qf /etc/httpd/conf/httpd.conf   # à quel paquet appartient ce fichier ?
      Avis de sécurité (updateinfo)
      Théorie

      Un avis de sécurité est une mise à jour qui corrige une faille ; chez AlmaLinux son nom commence par ALSA-, et il cite les CVE corrigées. Gravités : Critical, Important, Moderate, Low ; en production on passe d'abord Critical et Important.

      Pratique

      dnf check-update (liste, sans rien installer), dnf updateinfo summary (nombre d'avis par type et gravité), dnf updateinfo list --security, dnf updateinfo info <ALSA-…> (gravité, CVE). dnf update --security n'installe que les correctifs de sécurité : moins de changements, moins de risques.

      Exemple
      dnf updateinfo summary
dnf updateinfo list --security | head -3
dnf updateinfo info <identifiant ALSA-…>
      Question de révision

      Pourquoi préférer dnf update --security sur un serveur en production ?

      Réponse C. Seuls les correctifs de sécurité sont installés, ce qui limite les changements.

      Historique dnf (T19)

      Historique dnf et annulation
      Théorie

      Chaque action de dnf (installer, mettre à jour, supprimer) est une transaction numérotée dans l'historique. dnf history undo <n> fait l'inverse de la transaction n, et seulement de celle-là.

      Pratique

      dnf history (la plus récente en haut), dnf history info <n> (qui, quand, quels paquets), sudo dnf history undo <n> (last = la dernière).

      Exemple
      sudo dnf install -y tree
dnf history info last
sudo dnf history undo last -y
rpm -q tree               # package tree is not installed

      Annuler une mise à jour suppose que l'ancienne version soit encore dans les dépôts : ce n'est pas toujours le cas. Le vrai filet reste la sauvegarde ou l'instantané de la VM avant une grosse mise à jour. Une mise à jour du noyau ne sert qu'après un redémarrage.

      Question de révision

      Que fait sudo dnf history undo 12 ?

      Réponse A. undo inverse une seule transaction numérotée.

      Sauvegarde : tar et rsync (T20)

      Sauvegarde et règle 3-2-1
      Théorie

      Une sauvegarde est une copie des données gardée pour les restaurer après une perte. On sauvegarde les données et la configuration ; le système, lui, se réinstalle. Règle 3-2-1 : 3 copies, sur 2 supports différents, dont 1 hors du site.

      Pratique

      NordLog : /srv/nordlog, /srv/partages, /etc/samba, /etc/httpd/conf.d, vers /sauvegardes (2e disque, T13). Ce disque protège d'une erreur humaine ou d'une panne de disque, pas d'un incendie. Rétention : 7 jours.

      #### Archive et miroir

      Archive tar
      Théorie

      Une archive tar réunit des dossiers dans un seul fichier, compressé avec gzip (.tar.gz) : une photo datée par jour, qui garde un historique. tar retire le / de tête : l'archive contient srv/nordlog/….

      Pratique

      Options : -c créer, -t lister, -x extraire, -z gzip, -f le nom de l'archive (toujours en dernier), -C le dossier où extraire. Une sauvegarde n'existe que si on a testé la restauration.

      Exemple
      tar -czf /sauvegardes/archives/nordlog-$(date +%F).tar.gz /srv/nordlog /etc/samba /etc/httpd/conf.d
tar -tzf /sauvegardes/archives/nordlog-$(date +%F).tar.gz | grep compta
sudo tar -xzf /sauvegardes/archives/nordlog-$(date +%F).tar.gz -C / srv/nordlog/compta/<fichier>
      Miroir rsync
      Théorie

      Une copie à l'identique d'un dossier, mise à jour en ne recopiant que les différences : rapide, mais sans historique (seulement le dernier état).

      Pratique

      -a = copie fidèle (droits, dates) ; --delete supprime dans la copie ce qui a disparu de la source. Le / final de la source copie le contenu du dossier, pas le dossier lui-même.

      Exemple
      rsync -a --delete /srv/partages/ "$DEST/miroir/"

      Avec --delete, un fichier effacé par erreur disparaît aussi du miroir au passage suivant : seule l'archive datée permet de le retrouver.

      Question de révision

      Un fichier de compta a été effacé par erreur hier ; le miroir rsync --delete est passé cette nuit. Où le retrouver ?

      Réponse D. Avec --delete, le fichier a aussi disparu du miroir ; seule l'archive datée garde l'historique.

      Script de sauvegarde (T20)

      Script de sauvegarde Bash
      Théorie

      Un script réunit les commandes de la sauvegarde pour les lancer automatiquement. ${DEST:-/sauvegardes} garde DEST si elle existe déjà, sinon prend la valeur par défaut ; $(commande) met un résultat dans une variable ; les guillemets protègent les chemins ; >> ajoute sans écraser.

      Pratique

      /usr/local/bin/sauvegarde.sh, rendu exécutable (chmod 755), testé à la main, puis avec sudo DEST=/tmp/essai /usr/local/bin/sauvegarde.sh (DEST pour ce lancement seulement).

      Exemple
      #!/bin/bash
# sauvegarde.sh : sauvegarde quotidienne NordLog
DEST=${DEST:-/sauvegardes}
DATE=$(date +%F)
JOURNAL=/var/log/nordlog/sauvegarde.log
mkdir -p "$DEST/archives" "$DEST/miroir" /var/log/nordlog
tar -czf "$DEST/archives/nordlog-$DATE.tar.gz" /srv/nordlog /etc/samba /etc/httpd/conf.d 2>/dev/null
rsync -a --delete /srv/partages/ "$DEST/miroir/"
find "$DEST/archives" -name 'nordlog-*.tar.gz' -mtime +7 -delete
echo "$(date '+%F %T') sauvegarde terminée vers $DEST" >> "$JOURNAL"

      Tester un find … -delete en remplaçant d'abord -delete par -print : on voit ce qui serait supprimé sans rien supprimer. En cas d'échec, || logger -t sauvegarde "Échec de la sauvegarde" laisse une trace lisible avec journalctl -t sauvegarde.

      Question de révision

      Comment tester le script de sauvegarde sans écrire dans /sauvegardes ?

      Réponse B. ${DEST:-…} garde DEST si elle existe déjà ; on la fixe pour ce lancement seulement.

      Planifier avec cron (T20)

      Planification avec cron
      Théorie

      cron lance des commandes à heures fixes, de façon répétée. Une ligne : minute heure jour mois jour-de-semaine [compte] commande (* = tous).

      Pratique

      Dans /etc/cron.d/<fichier>, la ligne contient le compte entre l'horaire et la commande ; avec crontab -e, non. Les exécutions sont notées dans /var/log/cron.

      Exemple
      echo "30 22 * * * root /usr/local/bin/sauvegarde.sh" | sudo tee /etc/cron.d/nordlog-sauvegarde
      HoraireSe lit
      30 22 * * *tous les jours à 22 h 30
      0 3 * * 0chaque dimanche à 3 h
      */15 8-18 * * 1-5toutes les 15 min de 8 h 00 à 18 h 45, du lundi au vendredi

      cron travaille avec très peu de variables d'environnement : écrire des chemins complets. Dans une ligne cron, % doit s'écrire \%, sinon cron coupe la ligne : une raison de plus de mettre les commandes dans un script.

      Question de révision

      La sauvegarde du soir ne tourne pas ; /etc/cron.d/nordlog-sauvegarde contient 30 22 * * * /usr/local/bin/sauvegarde.sh. Quelle est la cause ?

      Réponse C. Dans /etc/cron.d, la ligne contient le compte entre l'horaire et la commande.

      Tâches ponctuelles at (J1, T21)

      La commande at
      Théorie

      at programme une commande pour plus tard, une seule fois ; elle s'exécute même si vous n'êtes plus connecté. Elle s'installe avec le paquet at et ne fonctionne que si le service atd est démarré.

      Pratique

      Filet de sécurité avant une modification risquée (SSH, réseau) : ① programmer la commande qui annule, 5 minutes plus tard ; ② modifier et tester ; ③ si tout marche, retirer le filet avec atrm (sinon, attendre : il annule tout seul).

      Exemple
      sudo dnf install -y at
sudo systemctl enable --now atd
echo "rm -f /etc/ssh/sshd_config.d/10-nordlog.conf && systemctl restart sshd" | sudo at now + 5 minutes
sudo atq          # liste les tâches et leur numéro
sudo atrm 1       # supprime la tâche 1
      Tâche ponctuelle avec at
      Théorie

      at programme une commande une seule fois, à une date et une heure données ; cron, lui, la répète. Les tâches sont exécutées par le service atd, qui doit tourner. Déjà vu au jour 1 comme filet de sécurité.

      Pratique

      La commande est passée par un | (sans echo : taper les commandes puis Ctrl+D). atq liste les tâches (numéro, date, compte), at -c <n> affiche leur contenu (la commande est à la fin), atrm <n> supprime. Pour déplacer une tâche : atrm, puis une nouvelle tâche.

      Exemple
      echo "systemctl restart httpd" | sudo at 23:30
echo "date >> /var/log/nordlog/maintenance.log" | sudo at now + 2 minutes
sudo atq
sudo at -c <numéro> | tail -3
sudo atrm <numéro>

      Autres horaires : at 08:00 tomorrow, at 07:30 2026-11-02.

      Rien ne se passe ? systemctl status atd. Ce qu'une tâche affiche n'apparaît pas à l'écran : la rediriger vers un fichier (>> /var/log/…). Le message warning: commands will be executed using /bin/sh est normal.

      Question de révision

      Une tâche at a été programmée mais rien ne s'est passé. Quel est le premier contrôle ?

      Réponse D. Les tâches at sont exécutées par le service atd, qui doit tourner.

      Journaux et automatisation

      journald et journaux Apache (T22)

      journald et journalctl
      Théorie

      journald (systemd) collecte les journaux des services ; journalctl les lit et les filtre. La priorité va de 0 (urgence) à 7 (débogage) ; 3 = err.

      Pratique

      Options combinables : -u <service>, --since today ou "1 hour ago", -b (depuis le démarrage), -p err (erreurs et plus grave), -f (en direct), -n 20 (20 dernières lignes), -t <étiquette> (messages écrits avec logger -t). Journal conservé après redémarrage si /var/log/journal existe ; taille : journalctl --disk-usage.

      Exemple
      journalctl -u httpd --since today    # lignes Started / Stopped = heure du dernier redémarrage
journalctl -u httpd -b -p err        # -- No entries -- si tout va bien
logger -t nordlog "test"
journalctl -t nordlog
      Journaux d'Apache
      Théorie

      Apache écrit ses propres fichiers dans /var/log/httpd/ : access_log (une ligne par visite : qui et quand) et error_log (le premier endroit à lire quand un site ne répond pas).

      Pratique

      Une ligne d'accès donne : l'adresse du visiteur, le compte web (- si la page n'est pas protégée), la date, la demande, le code de réponse et la taille, puis le programme du visiteur.

      Exemple
      192.168.100.10 - amartin [28/Oct/2026:10:15:02 +0100] "GET /direction/ HTTP/1.1" 200 17 "-" "curl/7.76.1"
      sudo tail -3 /var/log/httpd/access_log
      SourceContenu
      journalctl -u <service>le journal d'un service
      /var/log/messagesles messages généraux du système
      /var/log/secureles connexions et sudo
      /var/log/httpd/error_logles erreurs d'Apache
      /var/log/cronles exécutions de cron
      Question de révision

      Le site ne répond plus. Quelle commande affiche seulement les erreurs de httpd depuis le démarrage ?

      Réponse B. -u filtre le service, -b depuis le démarrage, -p err les erreurs et plus grave.

      Rotation des journaux (T22)

      Rotation avec logrotate
      Théorie

      La rotation renomme un journal, en ouvre un nouveau vide et supprime les plus anciens. Sans rotation, un journal grossit jusqu'à remplir /var : c'est la panne du T02.

      Pratique

      logrotate est lancé chaque jour par le minuteur systemd logrotate.timer, avec tous les fichiers de /etc/logrotate.d/. Directives : weekly/daily/monthly, rotate 4 (versions gardées), compress, missingok (pas d'erreur si absent), notifempty (pas de rotation d'un fichier vide), size 100M.

      Exemple

      /etc/logrotate.d/nordlog

      /var/log/nordlog/*.log {
    weekly
    rotate 4
    compress
    missingok
    notifempty
}
      sudo logrotate -d /etc/logrotate.d/nordlog   # simule, sans rien changer
sudo logrotate -f /etc/logrotate.d/nordlog   # force : fichiers .1.gz
df -h /var                                   # avant / après
      Question de révision

      /var se remplit de nouveau à cause de /var/log/nordlog. Quelle est la solution durable ?

      Réponse A. Sans rotation, un journal grossit jusqu'à remplir /var ; logrotate renomme, compresse et supprime les anciens.

      Ansible (bonus)

      Ansible
      Théorie

      Ansible applique la même configuration à de nombreuses machines, par SSH. On ne décrit pas des commandes, mais l'état voulu ; Ansible vérifie, puis agit seulement si c'est nécessaire. Rien à installer sur les postes gérés : SSH et Python suffisent.

      Pratique

      Nœud de contrôle : srv-infra (ansible-core) ; nœud géré : cli-01. Inventaire = les machines (en groupes) ; playbook = l'état voulu (YAML) ; module = l'action (user, group, dnf…) ; become: true = via sudo.

      Exemple
      printf "[postes]\n192.168.100.10 ansible_user=admin\n" > inventaire
ansible -i inventaire postes -m ping                    # "ping": "pong"
ansible-playbook -i inventaire nouvel-arrivant.yml -K   # -K : mot de passe sudo

  hosts: postes
  become: true
  tasks:
    - name: tree est installe
      ansible.builtin.dnf:
        name: tree
        state: present
      Idempotence
      Théorie

      Relancer le playbook ne change rien si tout est déjà conforme : le 2e lancement affiche changed=0.

      Pratique

      Dans nouvel-arrivant.yml : update_password: on_create (mot de passe posé une seule fois), register: compte (garder le résultat) et when: compte.changed (lancer chage -d 0 seulement si le compte vient d'être créé).

      Question de révision

      Pourquoi le 2e lancement d'un playbook affiche-t-il changed=0 ?

      Réponse B. Ansible décrit l'état voulu et n'agit que si c'est nécessaire.

      Dépannage et examen

      Méthode de dépannage

      Méthode de dépannage (examen du jour 4), toujours dans le même ordre : symptôme → service (systemctl status) → journal (journalctl -u <service> -b -p err) → réseau et pare-feu (ss -tulpn, firewall-cmd --list-all) → SELinux (ausearch -m avc -ts recent, ls -Z) → disque (df -h) → compte (id). Une seule correction à la fois, puis on reteste.

      Méthode de dépannage
      Théorie

      On reçoit un symptôme ; la différence se fait sur la méthode : regarder dans le bon ordre, au bon endroit, corriger une seule chose à la fois, puis retester.

      Pratique
      Exemple

      Cas guidé : « le site ne répond plus ».

      $ systemctl is-active httpd
failed
$ journalctl -u httpd -b -p err | tail -2
httpd[2210]: AH00526: Syntax error on line 4 of /etc/httpd/conf.d/intranet.conf:
httpd[2210]: Invalid command 'DocumentRot', perhaps misspelled
$ sudo vi /etc/httpd/conf.d/intranet.conf      # corriger DocumentRoot
$ sudo httpd -t && sudo systemctl restart httpd
Syntax OK
