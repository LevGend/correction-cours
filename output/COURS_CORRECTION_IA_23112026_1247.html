      DHCP

      Principe et configuration

      DHCP : distribuer les adresses
      Théorie

      Distribuer automatiquement l'adresse IP, la passerelle, le DNS et le domaine aux postes. Le serveur prête une adresse de sa plage pour une durée limitée : le bail. Une réservation donne toujours la même adresse à une machine, reconnue par son adresse MAC.

      Pratique

      Service dhcpd, configuré dans /etc/dhcp/dhcpd.conf : un bloc subnet avec la plage (range), un bloc host par réservation (fixed-address).

      Exemple

      Config finale /etc/dhcp/dhcpd.conf :

      option domain-name "nordlog.lan";
option domain-name-servers 192.168.100.1;
default-lease-time 600;
max-lease-time 7200;
authoritative;

subnet 192.168.100.0 netmask 255.255.255.0 {
    range 192.168.100.100 192.168.100.150;
    option routers 192.168.100.1;
    option broadcast-address 192.168.100.255;
}

host cli-01 {
    hardware ethernet 0e:ca:ac:db:36:79;
    fixed-address 192.168.100.10;
}
      Question de révision

      Comment le serveur DHCP reconnaît-il une machine pour lui donner toujours la même adresse (réservation) ?

      Réponse C. Une réservation associe une adresse MAC (hardware ethernet) à une adresse fixe (fixed-address) dans un bloc host.

      DNS

      Principe et outils

      DNS : traduire les noms en adresses
      Théorie

      Traduire un nom (intranet.nordlog.lan) en adresse IP. srv-infra fait autorité sur nordlog.lan et relaie vers 8.8.8.8 (forwarder) les noms qu'il ne connaît pas.

      Pratique

      named (bind) : paquets bind et bind-utils à installer sur srv-infra (bind-utils fournit dig). dig interroge un serveur DNS précis.

      Exemple
      dig @192.168.100.1 intranet.nordlog.lan +short
      dig @192.168.100.1 almalinux.org +short     # nom externe : la réponse passe par le relais 8.8.8.8
      Question de révision

      Que fait srv-infra lorsqu'on lui demande un nom qu'il ne connaît pas, comme almalinux.org ?

      Réponse B. srv-infra fait autorité sur nordlog.lan et relaie vers 8.8.8.8 les noms qu'il ne connaît pas.

      Configuration de named.conf

      listen-on port 53 { 127.0.0.1; 192.168.100.1; };   // écouter aussi sur le réseau privé
allow-query     { localhost; 192.168.100.0/24; };    // répondre au réseau privé
forwarders      { 8.8.8.8; };                        // relais pour les noms inconnus

zone "nordlog.lan" IN {
    type master;
    file "nordlog.lan.zone";     // relatif à /var/named/
};

      Les trois premières lignes se placent dans le bloc options { … } ; le bloc zone s'ajoute à la fin du fichier.

      Par défaut, bind n'écoute que sur 127.0.0.1 et ne répond qu'à localhost : il faut l'ouvrir explicitement au réseau privé.

      Question de révision

      Pourquoi faut-il modifier listen-on et allow-query dans named.conf ?

      Réponse C. Il faut ouvrir explicitement bind au réseau privé (192.168.100.1 et 192.168.100.0/24).

      Le fichier de zone

      Fichier de zone
      Théorie

      Le fichier qui décrit les noms d'un domaine (ici /var/named/nordlog.lan.zone). Chaque ligne = un enregistrement : <nom> IN <type> <valeur>.

      Pratique

      Déclaré dans named.conf (type master; file "nordlog.lan.zone";), lu par named ; vérifié avec named-checkzone. Types principaux : SOA, NS, A, CNAME.

      Exemple
      $TTL 3600
@   IN SOA srv-infra.nordlog.lan. admin.nordlog.lan. (
        2026112301 ; serial (AAAAMMJJnn) – à augmenter à chaque modif
        3600       ; refresh
        900        ; retry
        604800     ; expire
        300 )      ; TTL négatif
    IN NS    srv-infra.nordlog.lan.

srv-infra   IN A     192.168.100.1
cli-01      IN A     192.168.100.10
intranet    IN CNAME srv-infra
      TypeSensExemple
      SOAStart Of Authority : carte d'identité de la zone (obligatoire, en premier)@ IN SOA srv-infra.nordlog.lan. admin.nordlog.lan. ( … )
      NSName Server : quel serveur DNS répond pour la zoneIN NS srv-infra.nordlog.lan.
      Anom → Adresse IPv4cli-01 IN A 192.168.100.10
      CNAMEalias → vers un autre nomintranet IN CNAME srv-infra

      Règles des noms :

      • @ = le domaine lui-même (nordlog.lan.).
      • Nom court (cli-01) → bind ajoute le domaine → cli-01.nordlog.lan.
      • Nom qui finit par un point (srv-infra.nordlog.lan.) = nom complet, bind n'ajoute rien.
      • ⚠️ Nom complet sans point final → bind ajoute le domaine une 2e fois (srv-infra.nordlog.lan.nordlog.lan).
      • Une ligne qui commence par des espaces reprend le nom de la ligne au-dessus.
      Question de révision

      Que se passe-t-il si l'on écrit srv-infra.nordlog.lan (sans point final) dans un fichier de zone ?

      Réponse A. Seul un nom terminé par un point est complet ; sinon bind lui ajoute le domaine.

      Les 5 nombres du SOA

      ( 2026112301 3600 900 604800 300 )

      Ils servent quand il y a plusieurs serveurs DNS pour la même zone : un primaire (master, ici srv-infra) qui a le vrai fichier, et des secondaires (slaves) qui en gardent une copie. Les nombres disent aux secondaires comment rester à jour. Toutes les durées sont en secondes.

      PositionValeurNomCe que ça veut dire
      12026112301Serial (numéro de série)« Version » de la zone, au format AAAAMMJJnn (date + compteur du jour). Le secondaire compare ce numéro avec le sien : s'il est plus grand, il recopie la zone. ⇒ À augmenter à chaque modification, sinon les secondaires ne voient pas le changement. Maximum 10 chiffres.
      23600 (1 h)RefreshToutes les heures, le secondaire demande au primaire « ton serial a changé ? ».
      3900 (15 min)RetrySi le primaire ne répond pas, le secondaire réessaie toutes les 15 min.
      4604800 (7 jours)ExpireSi le primaire reste injoignable 7 jours, le secondaire arrête de répondre pour la zone (ses données sont trop vieilles pour être fiables).
      5300 (5 min)TTL négatifQuand un nom n'existe pas, les autres serveurs gardent cette réponse « n'existe pas » 5 min en cache avant de redemander.

      Moyen mnémotechnique : Série, Rafraîchir, Réessayer, Expirer, Négatif → « SRREN ».

      Dans notre TP il n'y a qu'un seul serveur DNS : seuls le serial et le TTL négatif ont un effet réel seul le TTL négatif a un effet réel ; le serial ne sert qu'aux secondaires, mais on l'augmente quand même à chaque modification (règle du cours, indispensable dès qu'un secondaire est ajouté). On met quand même les 5 valeurs car le format du SOA les exige.

      Question de révision

      Pourquoi faut-il augmenter le serial à chaque modification de la zone ?

      Réponse D. Sans serial plus grand, les secondaires ne voient pas le changement.

      Droits du fichier de zone

      -rw-r-----. root named   (640)

      named doit pouvoir lire (groupe named, r), personne d'autre ne doit y toucher. Même chose pour /etc/named.conf.

      sudo chown root:named /var/named/nordlog.lan.zone
sudo chmod 640 /var/named/nordlog.lan.zone
sudo restorecon -v /var/named/nordlog.lan.zone   # remet le contexte SELinux attendu
      Question de révision

      Pourquoi le fichier de zone est-il en root:named avec les droits 640 ?

      Réponse B. 640 = lecture-écriture pour root, lecture pour le groupe named, rien pour les autres.

      Vérifier puis démarrer

      sudo named-checkconf                                          # syntaxe de named.conf
sudo named-checkzone nordlog.lan /var/named/nordlog.lan.zone  # attendu : "OK"
sudo systemctl enable --now named
dig @192.168.100.1 intranet.nordlog.lan +short

Un service lit ses fichiers au démarrage : après un changement de droits ou de contenu, il faut le relancer.

      Réponse C. Un service lit ses fichiers au démarrage : après un changement de droits ou de contenu, il faut le relancer.

      NTP

      Chrony client et serveur

      NTP : la même heure pour tous
      Théorie

      Que toutes les machines aient la même heure (journaux, sauvegardes, certificats).

      Pratique

      chronyd, configuré dans /etc/chrony.conf : allow <réseau> pour servir l'heure, server <IP> côté client ; chronyc sources montre la source utilisée, marquée ^*.

      Exemple
      Machine/etc/chrony.confRôle
      srv-infrapool 2.almalinux.pool.ntp.org iburst + allow 192.168.100.0/24client d'Internet et serveur pour le réseau privé
      cli-01pool … remplacé par server 192.168.100.1client de srv-infra
      Question de révision

      Quelle directive permet à srv-infra de servir l'heure au réseau privé ?

      Réponse A. allow <réseau> autorise ce réseau à prendre l'heure sur le serveur ; server est le réglage côté client.

      Points pratiques

      • chronyd n'a pas de reload → sudo systemctl restart chronyd.
      • chronyc sources : la source utilisée est marquée ^* ; ^? = pas encore validée (attendre quelques échanges, colonne Reach). L'option iburst accélère la première synchronisation.
      • Sur cli-01, 192.168.100.1 s'affiche sous le nom _gateway (c'est sa passerelle).
      Question de révision

      Après avoir modifié /etc/chrony.conf, quelle commande faut-il utiliser ?

      Réponse D. chronyd n'a pas de reload : il faut le redémarrer.

      Pare-feu

      Zones firewalld

      Zones firewalld
      Théorie

      Une zone = un niveau de confiance, avec la liste des services autorisés pour ce qui arrive par elle. (La zone s'applique à l'interface, pas au subnet : le pare-feu regarde *par où* arrive le paquet.) Une zone se lie à une interface (par où arrive le paquet) ou à une source (un réseau, --add-source=…) ; ici, on la lie à l'interface.

      Pratique

      public pour le campus (le minimum), internal pour le réseau privé, où l'on ouvre DHCP, DNS et NTP. Sur AlmaLinux, la zone d'une interface se règle dans la connexion NetworkManager (connection.zone).

      Exemple
      sudo firewall-cmd --permanent --zone=internal --add-service={dhcp,dns,ntp}
sudo firewall-cmd --permanent --zone=public --remove-service=dhcp   # le campus n'en a pas besoin
sudo firewall-cmd --reload
sudo firewall-cmd --zone=internal --list-services
      InterfaceRéseauZonePourquoi
      ens33campus 10.226.21.0/24publicréseau partagé, peu de confiance : le minimum (ssh)
      vxlan0 (connexion lab)privé 192.168.100.0/24internalréseau de l'entreprise : on y ouvre DHCP, DNS, NTP

      Sur AlmaLinux, la zone se règle dans la connexion NetworkManager :

      sudo nmcli connection show lab | grep -i zone      # le réglage s'appelle connection.zone
sudo nmcli connection modify lab connection.zone internal
sudo nmcli connection up lab
sudo firewall-cmd --get-active-zones

      Les noms des réglages nmcli (connection.zone, ipv4.method, ipv4.dns…) ne se devinent pas : on les lit dans nmcli connection show <nom>, format réglage: valeur (-- = vide).

      Question de révision

      Pourquoi vxlan0 est-elle en zone internal et ens33 en zone public ?

      Réponse B. Le campus est peu fiable (seulement ssh) ; le réseau de l'entreprise est plus fiable, on y ouvre les services d'infrastructure.

      firewalld, nftables, iptables

      firewalld, nftables, iptables : un seul pare-feu
      Théorie

      firewalld (firewall-cmd) = l'outil qu'on utilise ; il écrit des règles nftables (nft), le moteur du noyau. iptables = l'ancien moteur.

      Pratique

      On administre avec firewall-cmd, on lit avec nft list ruleset. SSH est autorisé dans la chaîne filter_IN_public_allow (tcp dport 22 accept).

      Exemple
      sudo nft list ruleset | grep -nE "chain |dport 22"
      • Lire les règles actives : sudo nft list ruleset (filtrer : | grep -nE "chain |dport 22" ; le nombre en début de ligne est le numéro de ligne de grep -n, pas le port).
      Question de révision

      Quel est le lien entre firewalld et nftables ?

      Réponse C. On administre avec firewall-cmd, qui produit des règles nftables qu'on lit avec nft list ruleset.

      Règles nftables

      Table, chaîne, politique et règles nftables
      Théorie

      Une table regroupe des chaînes ; une chaîne est accrochée à un moment du trajet du paquet (hook input = ce qui arrive) et a une politique par défaut ; les règles sont lues dans l'ordre, la première qui correspond décide.

      Pratique

      Le -j DROP final devient la politique de la chaîne (policy drop).

      Exemple

      /root/regles.nft :

      table inet nordlog {
    chain input {
        type filter hook input priority 0; policy drop;
        iif "lo" accept
        ct state established,related accept
        tcp dport 22 accept
        ip protocol icmp accept
    }
}
      • sudo nft -c -f /root/regles.nft : vérifie sans appliquer (-c = check). Ne jamais l'appliquer (-f seul) : un 2e pare-feu bloquerait DNS, DHCP, NTP…
      Question de révision

      Pourquoi ne faut-il jamais appliquer /root/regles.nft avec nft -f seul ?

      Réponse D. La chaîne en policy drop n'autorise que lo, les connexions établies, SSH et ping : les services d'infrastructure seraient bloqués.

      Dépannage réseau

      Méthode du bas vers le haut

      Méthode de dépannage réseau
      Théorie

      Un réseau fonctionne par étages : chaque étage a besoin de celui du dessous. On teste donc du bas vers le haut, et on s'arrête au premier test qui échoue.

      Pratique

      adresse → passerelle → route → nom → service : ip -br a, ping <passerelle>, ip route + ping 8.8.8.8, /etc/resolv.conf + getent hosts, ss -tulpn (ports à l'écoute).

      Exemple
      Test qui échoueCe que ça veut dire
      pas d'adressela carte ou le DHCP ne marche pas
      la passerelle ne répond pasle lien vers le routeur est coupé (câble, tunnel, pare-feu)
      pas de ligne default dans ip routela machine ne sait pas où envoyer ce qui sort du réseau local
      ping 8.8.8.8 OK mais pas les nomsproblème de DNS : voir /etc/resolv.conf
      Question de révision

      Pourquoi teste-t-on du bas vers le haut en s'arrêtant au premier test qui échoue ?

      Réponse C. Si un étage échoue, tous ceux du dessus échoueront aussi : inutile de les tester.

      Où se règle le DNS

      Ce que j'ai appris :

      Où se règle le DNS d'une machine
      Théorie

      On ne corrige pas /etc/resolv.conf à la main : il est réécrit par NetworkManager. On corrige la connexion.

      Pratique

      nmcli connection modify enregistre ; nmcli connection up applique. nmcli connection show <nom> affiche tous les réglages d'une connexion.

      Exemple
      $ ping -c1 8.8.8.8
64 bytes from 8.8.8.8: icmp_seq=1 ttl=115 time=12.3 ms
$ ping -c1 almalinux.org
ping: almalinux.org: Name or service not known
$ cat /etc/resolv.conf
nameserver 10.9.9.9

      Internet répond par adresse, mais pas par nom : le DNS 10.9.9.9 est faux, on le corrige dans la connexion avec nmcli.

      • Mieux vaut rendre le DNS au DHCP que le forcer en dur : si le DNS change, on ne modifie que dhcpd.conf.
      • Symptôme d'un DNS mort en 1re position : tout est lent (ping de 3 paquets en 6 s) car le système attend le délai d'expiration avant de passer au DNS suivant.
      • Tester un serveur DNS précis : dig @8.8.8.8 google.com +short (sans nom, dig renvoie les serveurs racine).
      • Ne modifier que ce que la panne a changé (j'ai touché ipv6.never-default sans raison, puis je l'ai remis).
      Question de révision

      Pourquoi ne corrige-t-on pas /etc/resolv.conf à la main ?

      Réponse D. /etc/resolv.conf est régénéré par NetworkManager ; la modification doit se faire dans la connexion avec nmcli.

      • Rapport complet et précis sur le DHCP, le DNS (zone, SOA, point final, droits, ordre des opérations) et NTP, avec les commandes de vérification avant démarrage.
      • T10 : méthode du bas vers le haut appliquée, deux causes bien nommées, distinction nmcli modify (enregistre) / up (applique), et réponse au ticket rédigée en cause, correction, prévention.
      • T11 : tableau iptables vers nftables juste et regles.nft correct, avec le bon réflexe nft -c sans appliquer.
      • Excellente auto-analyse (« Mes points à améliorer ») : erreurs récurrentes identifiées avec une action concrète.
      • Beaucoup de recherche personnelle exacte (ProxyJump, SOA, comportement de dhcpd, _gateway).

      À améliorer

      • Pare-feu : toujours préciser la zone (--zone=internal) en ouvrant un service, sinon c'est la zone par défaut (public) qui est modifiée ; penser aussi à fermer ce qui est inutile (dhcp dans public).
      • Ne pas noter de généralités non vérifiées (--now « seulement avec enable/disable », « la zone s'applique à l'interface, pas au subnet ») : vérifier dans man ou la doc officielle.
      • Noter les installations de paquets (bind, bind-utils) et les commandes de droits/SELinux (restorecon) en plus de la valeur des droits.
      • T10 : ajouter l'étape « le service écoute-t-il ? » (ss -tulpn) qui ferme la méthode d'étage en étage.
      • T11 : retenir que l'ordre des règles compte (la première qui correspond décide).
      • Aucun [?] laissé dans les notes : rien à combler. Ce n'est pas un défaut, mais écrire [?] quand une notion est floue (ex. le rôle réel du serial) aurait compté pour une demi-notion.
      • Périmètre : T12 à T16 (processus, disque, NFS/autofs, Samba, Cockpit/Podman) n'ont pas été notés ; ils ne comptent pas dans la note mais restent à revoir.

      Erreurs relevées

      • firewall-cmd --permanent --add-service=dhcp (sans zone) → --permanent --zone=internal --add-service=dhcp : sinon le service est ouvert dans public.
      • « La zone s'applique à l'interface, pas au subnet » → une zone se lie à une interface ou à une source (réseau, --add-source).
      • « --now ne va qu'avec enable/disable » → il va aussi avec mask.
      • « Seuls le serial et le TTL négatif ont un effet réel » (un seul serveur DNS) → seul le TTL négatif ; le serial ne sert qu'aux secondaires.
      • Brouillon : range 192.168.100.10 dans host → fixed-address 192.168.100.10;.
      • Brouillon : option routers rtr-239-0-1.example.org, … → option routers 192.168.100.1;.
      • Brouillon : broadcast-address 192.168.100.1 → 192.168.100.255.
