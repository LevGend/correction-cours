      Fondamentaux de la virtualisation

      Types d'hyperviseurs

      Type 1 : (serveur) l'hyperviseur s'exécute directement sur le matériel (bare metal).

      • Nutanix (AHV)
      • Proxmox
      • XCP-NG
      • Hyper-V
      • VMware
      • ESXi

      Type 2 : (maquette PC) l'hyperviseur s'exécute comme une application sur un OS hôte.

      • VMware Workstation
      • VirtualBox

      Fournisseurs :
      Dell, HPE

      Lexique

      • VDI : Virtual Desktop Infrastructure (ex : Citrix, xcp-ng)
      • Nested : Virtualisation imbriquée (un hyperviseur dans une VM)
      • Emulation : Faire fonctionner une architecture sur une autre architecture, traduction des instructions. (ARM => x86 par exemple)
      • Bare Metal : Utilisation d'un serveur sans virtualisation (on parle aussi d'hyperviseur bare metal pour un type 1)
      • Cluster : Groupe de nœuds (serveurs physiques)
      • KVM : Kernel-based Virtual Machine
      • PRA : Plan de reprise d'activité
      • PCA : Plan de continuité d'activité

      Ressources et machines virtuelles

      Dimensionnement et surallocation

      • Surallocation : Allouer plus que ce que la machine possède physiquement

      Dimensionnement d'un serveur physique
      Pour 1 Go de RAM physique, en allouer 4-5, pour une base de données, 1 pour 1

      Le ratio 4-5:1 est la règle habituelle pour les vCPU par cœur physique ; la surallocation de RAM reste en général bien plus modérée.

      Gestion de la mémoire

      • SWAP : l'utilisation d'un espace de stockage secondaire (disque dur ou SSD) pour étendre la mémoire vive (RAM)
      • Memory Tiering : hiérarchisation de la mémoire (RAM + niveau plus lent, par ex. NVMe) pour étendre la capacité.
      • Ballooning : Allocation dynamique de la mémoire par l'hyperviseur
        • Fait gonfler la mémoire d'une VM pour la forcer à swapper (le driver « ballon » réserve de la RAM dans l'invité, que l'hôte récupère).
        • ⚠️Drivers VirtIO requis
      • Swap : Utilisation du stockage pour libérer de la RAM
      • TPS : Transparent Page Sharing
        • Mutualisation de la mémoire pour la même ressource (pages identiques fusionnées en une seule copie).
        • 💡VMware uniquement
        • 🐧KSM : Kernel Samepage Merging (équivalent Linux/KVM, utilisé par Proxmox)
      • Compression : Utilise des mécanismes de compression. Coût en CPU.

      GPU et compatibilité CPU

      • CUDA : SDK propriétaire NVIDIA permettant de déléguer des calculs généralistes (parallèles) au GPU
      • EVC (VMware) Enhanced vMotion Compatibility : masque les jeux d'instructions CPU pour permettre le vMotion entre générations de processeurs différentes.

      Paramètres réseau des VM

      Bridge : récupère paramètres NIC physique (la VM est directement sur le réseau physique)
      NAT : traduction d'adresses : la VM sort avec l'IP de l'hôte
      LAN Segments : Segments LAN virtuels sur Workstation

      Stockage et Ceph

      Provisionnement

      • Thin Provisioning : Méthode d'allocation du stockage dynamique : l'espace disque n'est réellement consommé qu'au fur et à mesure de l'écriture des données.
      • Thick Provisioning : Allocation de toute la taille du disque à sa création
        • Lazy-zeroed : espace réservé immédiatement, mais les blocs ne sont mis à zéro qu'à la première écriture.
        • Eager-zeroed : Intégralité de l'espace est pré-allouée et remplie de zéros dès sa création

      Types de stockage

      • NFS : Network File System

      RAID : redondance des données (sauf RAID 0) :
      RAID 1 : Copie conforme des disques
      LVM-thin : disques de VM et conteneurs (stockage bloc : pas d'ISO)
      ZFS : système de fichiers + gestionnaire de volumes (copy-on-write, snapshots, checksums, RAID-Z), local au nœud.
      NFS : marche bien sauf quand latence. SPOF. Système de verrouillage (lck)
      iSCSI : stockage bloc partagé pour les disques de VM (les ISO vont sur un stockage fichier)

      LVM-thinThin provisioning + snapshotsLocal uniquement (non partageable)
      LVM sur iSCSIPerf bloc, Live MigrationPas de snapshots (possibles depuis PVE 9 en tech preview, « volume chains »), Thick only
      Shared LVMSnapshots via volume chains (PVE 9, tech preview) ; pas de thin provisioningComplexité réseau (Fabric)

      Ceph est un système de stockage dans un environnement de cluster (open source Linux), qui stocke et protège les données grâce à la réplication

      Pools et placement groups

      MTU et cartes réseau

      • MTU : Taille maxi d'un paquet (charge utile d'une trame, en-têtes Ethernet exclus). Standard : 1500 ; jumbo frames : 9000.
      • Smart NIC : Carte réseau avec CPU (pour de la virtualisation notamment)
        • check MTU avec ping :
      ping -f -l 8972 [destinationIP]

      Syntaxe Windows : -f interdit la fragmentation, -l fixe la taille des données. 8972 = 9000 − 20 (en-tête IP) − 8 (en-tête ICMP). Sous Linux : ping -M do -s 8972 [destinationIP].

      En gros ça permet de ne pas sortir du nœud physique pour 2 VM sur des réseaux différents.

      Cluster et haute disponibilité

      Topologies de cluster

      2 nœuds : économique. Nécessite QDevice pour le quorum
      3 nœuds (Hyperconvergence) : Standard, quorum naturel (2/3). Idéal pour Ceph
      Stretched : Multi-site. Haute tolérance aux pannes

      • Stretched cluster : cluster dont les nœuds sont répartis sur deux sites (plus un témoin pour le quorum), avec stockage répliqué entre les sites.

      Corosync et quorum

      Moteur de clustering : communication entre nœuds, appartenance au cluster et quorum. Sensible à la latence : réseau dédié recommandé.

      • Quorum : le nombre minimum de membres qui doivent être présents ou représentés au sein d'une assemblée délibérante pour que ses décisions et ses votes soient valables → dans un cluster : majorité des votes (N/2 + 1) nécessaire pour agir, afin d'éviter le split-brain.
      • QDevice : Pour faire le quorum : vote externe (service corosync-qnetd sur une machine tierce) qui départage un cluster à nombre pair de nœuds.

      Haute disponibilité (HA)

      • Fault tolerance, Haute disponibilité : la Fault Tolerance maintient une copie synchrone de la VM qui prend le relais sans interruption ; la HA redémarre la VM sur un autre nœud après une panne (courte coupure).

      CRM : Cluster Resource Manager (+ LRM : Local Resource Manager sur chaque nœud)
      Watchdog : si le nœud perd le quorum, le watchdog n'est plus réarmé et le nœud redémarre (self-fencing).
      STONITH : Shoot The Other Node In The Head
      Éviter la corruption
      S'assure qu'un nœud injoignable est bien éteint
      Best Practice : Ne rien faire
      Maîtriser le placement
      Priority (0-100) : La VM va sur le nœud avec le plus haut score
      Restricted : Strict. La VM ne tourne que sur les nœuds définis (groupes). Si pas de dispo, VM arrêtée
      No-Failback : la VM ne revient pas automatiquement sur le nœud prioritaire quand il redevient disponible.
      Depuis PVE 9, les groupes HA sont remplacés par les « Node Affinity Rules ».
      Sur VMware : Should/Must : Prioriser/forcer. Must not : Interdire le lancement sur un groupe d'hôtes (Should not : l'éviter).

      Points forts et à améliorer

      Points forts

      • Lexique très fourni, qui sert de bon aide-mémoire.
      • Journal de TP détaillé : chaque problème est accompagné de sa cause et de sa solution (hostname incohérent, dépôts, accès Internet, NTP).
      • Bonne compréhension du Live Migration (pre-copy, dirty pages, stop & copy) et du fonctionnement des API tokens.
      • Tableau RAID complet et juste.

      À améliorer

      • Sécurité : ne stocke jamais de mots de passe en clair dans tes notes, même de TP (ils finissent copiés, synchronisés, partagés). Utilise un gestionnaire de mots de passe ou note seulement « voir coffre ».
      • Compléter les définitions laissées vides ou tronquées au moment du cours, ou les marquer « à compléter ».
      • Ranger chaque notion à sa place (Corosync dans Cluster/HA, pas dans Système de fichiers) et regrouper les deux sections Hyperconvergence.
      • Remplir les tableaux commencés (stockage, rôles) ou les supprimer.
      • Vérifier les ordres de grandeur (latence, ratios de surallocation) : un signe inversé change tout le sens.

      Erreurs relevées

      • Corosync rangé dans « Système de fichiers » → c'est la couche de communication du cluster ; le système de fichiers du cluster est pmxcfs (/etc/pve).
      • Ceph « Latence >1ms » → latence la plus faible possible, inférieure à 1 ms.
      • « Minimum Size : nombre minimum de nœuds » → min_size = nombre minimal de réplicas disponibles pour accepter les I/O.
      • LVM-thin et iSCSI « pour les ISO » → stockages bloc pour disques de VM (et conteneurs pour LVM-thin) ; les ISO vont sur un stockage fichier.
      • Shared LVM « Thin provisioning » → pas de thin provisioning en LVM partagé ; snapshots possibles depuis PVE 9 (tech preview).
      • Compression « coût en mémoire » → coût en CPU.
      • Ballooning « par l'hyper-V » → par l'hyperviseur.
      • VDI « Virtual Desktop Instance » → Virtual Desktop Infrastructure.
      • « 2018 V5 : intégration native Ceph » → V5 sortie en 2017 ; Ceph intégré depuis la 3.2 (2014).
      • PBS « Proxmox Backup Service » → Proxmox Backup Server.
      • « Une sauvegarde testée n'existe pas » → « Une sauvegarde non testée n'existe pas ».
      • Fautes de termes : Hyperconergeance/Hyperconvergeance → Hyperconvergence, Eger-zeroed → Eager-zeroed, Memory Tearin → Memory Tiering, enol → eno1, Netword → Network, Roxmox → Proxmox, Keycloack → Keycloak, PVEVMADMIN → PVEVMAdmin, PVE 01 en double → PVE 02.

      Pistes

      • Ceph hyperconvergé : relis les prérequis matériel et réseau (10 Gbps minimum, HBA plutôt que RAID) puis termine ton TP en créant les OSD et le pool : https://pve.proxmox.com/wiki/Deploy_Hyper-Converged_Ceph_Cluster
      • Placement Groups et autoscaler : comprends comment Ceph répartit les données et teste ceph osd pool autoscale-status : https://docs.ceph.com/en/latest/rados/operations/placement-groups/
      • HA Proxmox : fencing par watchdog, nofailback, Node Affinity Rules (qui remplacent les groupes HA depuis PVE 9). Exercice : coupe brutalement un nœud et chronomètre la reprise de ta VM : https://pve.proxmox.com/wiki/High_Availability
      • SDN : crée une zone VXLAN entre tes 3 nœuds et un VNet, puis fais communiquer deux VM : https://pve.proxmox.com/pve-docs/chapter-pvesdn.html
      • Proxmox Backup Server : installe PBS dans une VM, sauvegarde une VM chiffrée puis teste un Live Restore : https://pbs.proxmox.com/docs/
      • Jumbo frames : passe ton réseau Ceph en MTU 9000 et valide avec ping -M do -s 8972 <IP> sous Linux.
